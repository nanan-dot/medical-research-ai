==================================================
四、视觉设计方向
==================================================

整体视觉采用：

“月之暗面式稳定产品结构 + 编辑式医学科研视觉 + 证据优先界面”。

综合以下设计特征：

1. 月之暗面/Kimi：
   - 稳定的左侧导航；
   - 顶部全局工具栏；
   - 清晰的中央工作区；
   - 用户容易理解的任务入口；
   - 低学习成本。

2. Awwwards：
   - 高级构图；
   - 页面节奏；
   - 克制的品牌感；
   - 细腻动效。

3. Behance：
   - 完整Design System；
   - 统一排版、色彩和视觉叙事。

4. Dribbble：
   - 按钮、输入框、状态标签、抽屉和交互细节精致。

5. Nature / Science / PubMed：
   - 科研可信感；
   - 文献信息清楚；
   - 引用、页码、证据和研究类型优先；
   - 不娱乐化。

6. 摄影网站：
   - 首页可使用克制的大图或科研抽象视觉；
   - 大面积留白；
   - 编辑式布局；
   - 自然微动画。

禁止：

- 普通后台模板；
- 大量同质Card堆叠；
- 赛博朋克；
- 蓝紫霓虹；
- 随机粒子；
- 机器人医生；
- 发光DNA背景；
- 过度玻璃拟态；
- 所有组件统一超大圆角；
- 为视觉效果牺牲文献阅读效率；
- 直接复制其他产品商标、图片和具体页面。

七、页面详细要求
==================================================

-----------------------------
01 工作台首页
-----------------------------

页面目标：让医学研究生进入系统后立即知道下一步，而不是看到统计卡片墙。

布局：

- 顶部问候、当前模型、隐私状态；
- 中央大输入框：输入研究问题、论文问题或检索主题；
- 5个核心快速入口：证据问答、文献检索、论文分析、研究方向、写作辅助；
- 最近任务；
- 运行中任务；
- 知识库健康状态；
- 最近论文、会话和检索；
- 轻量统计放在底部，不成为首页核心。

主操作只能有一个，例如“继续上次研究”。

禁止使用10个同样大小的功能Card。

-----------------------------
02 论文分析
-----------------------------

布局：

- 左侧PDF页缩略图或章节目录；
- 中央论文内容和结构化分析；
- 右侧证据定位；
- 顶部论文标题、模板、版本、导出、加入对比；
- 底部或末尾显示研究类型、发布日期、引用和证据状态。

结构化字段：

- 研究背景；
- 科学问题；
- 研究类型；
- 研究对象；
- 样本量；
- 干预/暴露；
- 对照；
- 结局；
- 统计方法；
- 主要结果；
- 创新点；
- 局限性；
- 待确认项。

每个字段必须可点击查看来源。

-----------------------------
03 证据问答
-----------------------------

布局：

- 左侧历史会话；
- 中央论文式回答；
- 右侧引用原文；
- 底部问题输入；
- 顶部文档范围和模型。

回答不能只使用普通聊天气泡。

必须突出：

- 来源序号；
- 论文标题；
- 页码；
- 章节；
- 原文片段；
- 无答案；
- 不确定性；
- 引用正确性反馈。

-----------------------------
04 文献检索
-----------------------------

当前后端只完成到R2-WP02，因此真实可用范围是：

- 自然语言主题输入；
- 研究需求结构化；
- 疾病、干预、机制、时间和文献类型编辑；
- 关键词组；
- 同义词；
- MeSH候选；
- AND/OR结构；
- 最终PubMed检索式预览和复制。

R2-WP03真实PubMed搜索未完成时：

- 结果列表只能使用Mock Adapter；
- 页面明显显示“结果区域为前端演示数据，真实PubMed接口待R2-WP03接入”；
- 不得把Mock论文写入真实数据库；
- 不得显示为真实检索完成；
- 不得伪造接口耗时和结果数。

布局：

- 顶部大搜索框；
- 条件标签；
- 左侧检索构建器；
- 中央演示结果或未接入状态；
- 右侧检索式预览；
- PubMed严谨信息密度；
- 不做摄影作品墙。

-----------------------------
05 知识库

==================================================

```ts
export type FeatureAvailability = 'live' | 'mock' | 'unavailable'
```

建议配置：

```ts
export interface FrontendFeatureFlags {
```

==================================================
十一、强制代码规范
==================================================

1. 一个文件只负责一个主要功能；
2. 禁止所有代码写在一个文件；
3. 每个组件必须独立封装；
4. 页面组件只负责编排；
5. API请求统一放入API层；
6. 跨页面状态放入Pinia；
7. 可复用交互放入Composable；
8. TypeScript类型独立管理；
9. 禁止大量`any`；
10. 不生成无意义代码；
11. 不生成未来可能使用但当前无调用方的空组件；
12. 不做与当前前端任务无关的后端重构；
13. 不一次把所有逻辑塞进`App.vue`或单个页面；
14. 复杂组件超过约300—400行时检查是否需要拆分；
15. 文件达到约600行必须说明不拆分理由；
16. Design Token统一管理颜色、字体、间距、圆角、阴影和动画；
17. 禁止页面中散落大量硬编码颜色；
18. 禁止重复实现Button、Badge、Dialog和状态组件；
19. 不引入没有明确使用场景的大型UI库；
20. 不擅自更换技术栈。

==================================================

==================================================

- 无限装饰动画；
- 大幅弹跳；
- 高频视差；
- 干扰阅读；
- 多个区域同时持续运动。

必须支持：

- `prefers-reduced-motion`；
- 键盘操作；
- `focus-visible`；
- 图标按钮可访问名称；
- 表格语义；
- 状态不只依赖颜色；
- 合理对比度；
- 长文合理行宽。
