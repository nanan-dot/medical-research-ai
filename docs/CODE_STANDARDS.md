# 代码生成强制规范 V2.0（增强版）

> 基于 V1.0 十五条规定，融合 Google Python Style Guide、PEP 8、Airbnb JavaScript Style Guide、Vue 官方风格指南、阿里巴巴 Java 开发手册的工程化原则修订。
> 适用范围：本仓库全部代码（FastAPI 后端 / Vue3+TS 前端 / 脚本 / 测试）。
> 版本：V2.0 ｜ 更新：2026-08-04 ｜ 维护：本人

---

## 一、总体原则

1. **一个文件只负责一个功能**；禁止把所有代码堆在一个文件里。
2. **每个组件独立封装**；组件边界清晰，可独立测试、独立替换。
3. **分层合理**：后端分离 `入口 / 路由 / 业务 / 数据访问 / 工具 / 配置 / 模型`；前端分离 `API / Types / Store / Composable / View / 组件`。目录结构体现分层，禁止业务逻辑混入入口文件。
4. **代码是写给人看的**：可读性 > 炫技；优先简单直白的实现，不做过度设计。

---

## 二、命名与类型

5. **命名语义化**：禁止 `a`、`tmp`、`data2`、`handler1` 等无意义命名；名称必须表达意图（动词+宾语、名词短语）。
6. **类型注解**（Python）：所有函数参数与返回值添加类型注解；复杂类型使用 `TypeAlias` 或 Pydantic 模型；禁止 `Any` 泛滥。
7. **类型标注**（前端 TS）：禁止隐式 `any`；props/emit/ref 均需显式类型；复用类型统一收口到 `types/` 或组件内具名导出。
8. **命名规范**：
   - Python：`snake_case` 函数/变量、`PascalCase` 类、`UPPER_SNAKE` 常量、`_private` 内部成员、`__all__` 声明对外接口。
   - TS/JS：`camelCase` 函数/变量、`PascalCase` 组件/类型/接口、`SCREAMING_SNAKE` 常量、`kebab-case` 文件与路由。
   - 布尔变量用 `is_/has_/should_` 前缀；集合用复数；回调用 `onXxx`、事件用 `handleXxx`。
9. **抽取常量**：消除魔法数字与魔幻字符串；配置类值（URL、超时、阈值）放入常量或配置模块，禁止散落业务代码。

---

## 三、注释规范（设计意图，不是复述）

10. **复杂逻辑添加有意义的中文注释，重点说明"为什么这样设计"**（设计思路、权衡、坑），不要复述代码行为（"遍历列表"这种注释是噪音）。
11. **简单逻辑无需冗余注释**；命名已自解释的代码不重复注释。
12. 公共函数/组件写 Docstring/JSDoc：`一句话职责 + 参数说明 + 返回值 + 异常`；内部工具函数可只写一行意图。
13. `TODO/FIXME/HACK` 必须标注负责人与原因，禁止无说明悬挂。

---

## 四、函数与组件设计

14. **优先纯函数**：相同输入必有相同输出；副作用（IO、状态变更）隔离到明确边界，不在纯函数内藏副作用。
15. **减少全局变量**：全局状态必须收敛到明确容器（Store/Config/Session），禁止散落模块级可变变量。
16. **大型类及时拆分**：一个类超过约 300 行或职责超过一个，必须拆分（混入、组合、子模块）；避免 God Object / 单体臃肿。
17. **函数短小**：单个函数超过约 40 行应审视拆分；一个函数只做一件事（单一职责的粒度）。
18. **接口最小暴露**：仅对外导出必要方法；内部工具函数私有化（`_` 前缀 / 不 export）；主动规避循环依赖（依赖方向单向，模块间不互相 import）。

---

## 五、异常处理

19. **禁止空捕获、裸 `except`**：捕获必须指定异常类型，并给出处理（记录、转换、重抛）。
20. **异常要"可吞则吞、该抛则抛"**：可恢复的异常局部处理并记录；不可恢复的向上抛出或转换为领域异常。
21. 禁止用 `except Exception: pass` 掩盖错误；至少 `logger.warning` 记录原因。
22. 跨层传递时保留原始异常链（`raise ... from e`）；不要丢失根因。

---

## 六、依赖管理

23. **优先标准库**：能标准库解决不引入第三方依赖。
24. **区分必选/可选依赖**：核心功能依赖进 `dependencies`，开发/测试/可选功能进 `optional-dependencies`（如 `dev`、`rag` 分组）。
25. 引入新依赖必须说明用途；同一能力不重复引入多个库（如不同时用两个 HTTP 客户端）。
26. 前端依赖锁定版本；后端用版本范围（`>=`）并保留 lock 文件。

---

## 七、安全与合规

27. **不生成恶意高危脚本代码**：不产出后门、窃密、破坏性命令、未授权操作。
28. **密钥零泄漏**：API Key / Token / 密码只进 `.env`（gitignore），严禁硬编码、严禁写入日志、严禁提交仓库；代码中只引用环境变量。
29. **输入校验**：外部输入（请求体、文件、URL 参数）必须校验后再使用；路径拼接防目录穿越；SQL 防注入（用 ORM 参数化）。
30. **日志脱敏**：日志中禁止打印敏感字段；个人/医学数据遵守最小化原则。
31. **提示安全风险**：代码存在性能、并发、安全隐患时，主动向使用者提示风险与缓解建议。

---

## 八、验证与诚实（最高优先级）

32. **未实际运行的命令、方案不得声称"验证通过"**；无法实测的内容必须标注【未实测】。
33. **严禁虚构运行日志、执行结果、测试报告**；所有"通过/成功/完成"必须以真实工具输出为依据。
34. 涉及数据（论文、DOI、PMID、页码、统计值）禁止伪造；无法获取必须如实说明。
35. 交付前必须实际运行：后端 `pytest` + `ruff` + `mypy`；前端 `typecheck` + `lint` + `build`；未运行不得声称通过。

---

## 九、输出与交付

36. **输出多文件代码时，先提供完整项目目录树**，每个代码块标明文件路径（如 `app/services/paper.py`），文件间引用关系清晰。
37. **输出配套调用示例、启动方式**：如何安装依赖、启动服务、调用接口/组件，示例可运行。
38. **不生成无意义代码**：不做冗余占位函数、重复样板代码、死代码；删除未使用的 import 与变量。
39. 交付说明列出：改动文件清单、验证结果（真实命令输出）、已知限制与【未实测】项。

---

## 十、测试规范

40. 核心逻辑必须配套测试：单元测试覆盖业务函数，接口测试覆盖路由；测试命名 `test_行为_期望结果`。
41. 测试不依赖真实网络/外部服务；外部依赖用 mock 或测试替身；测试数据用 fixture。
42. 测试是代码的一部分，同样遵守命名与注释规范；禁止只写"能跑通"的无断言测试。
