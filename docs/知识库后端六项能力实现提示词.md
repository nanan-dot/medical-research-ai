# 5. 能力一：真正的自动同步

## 5.1 业务定义

`auto_sync=true` 必须代表系统会在符合条件时自动投递持久化同步任务，而不是只保存一个布尔字段。

自动同步必须满足：

- 使用现有持久化任务系统；
- 调度器只负责发现到期来源并投递任务，不直接扫描文件；
- Worker 继续负责实际同步；
- 同一来源在同一时间最多存在一个活动同步任务；
- 多调度器实例并发运行时不会重复投递；
- 服务重启后任务仍存在；
- 失败任务遵循明确重试/退避策略；
- 已暂停、不可用或 `auto_sync=false` 的来源不会被自动投递；
- 手动同步与自动同步共享幂等键和互斥规则；
- 不使用 FastAPI `BackgroundTasks`、裸 `asyncio.create_task` 或进程内定时器冒充持久化调度。

## 5.2 数据模型

根据现有字段审计后，最小化增加：

```text
sync_interval_minutes: int
next_auto_sync_at: datetime | null
last_auto_sync_enqueued_at: datetime | null
auto_sync_failure_count: int
```

如果任务表已有 `scheduled_at`、重试次数和幂等键，优先复用。所有时间使用 UTC。为到期查询增加合适索引，例如：

```text
(auto_sync, enabled, next_auto_sync_at)
```

不得直接把本地时区时间写入数据库。

## 5.3 调度策略

实现纯函数计算下一次调度时间，并由独立 Scheduler 服务执行：

```text
查找到期来源
→ 以数据库锁或原子更新方式声明调度权
→ 调用现有 KnowledgeSourceSyncTaskService.enqueue
→ 更新 next_auto_sync_at
→ 提交事务
```

SQLite 与生产数据库的并发能力可能不同。必须根据当前数据库支持采用可验证方案，不能假定 `SKIP LOCKED` 在 SQLite 可用。

## 5.4 API

扩展来源更新契约，至少支持：

```json
{
  "auto_sync": true,
  "sync_interval_minutes": 60
}
```

验证范围必须由配置常量定义。关闭自动同步时清除或停用下一执行时间，但不得删除正在运行的手动任务。

## 5.5 验收标准

- AC-AUTO-01：开启自动同步并到期后，只产生一个持久化同步任务。
- AC-AUTO-02：两个 Scheduler 并发处理同一来源，不会产生重复活动任务。
- AC-AUTO-03：关闭、暂停、不可用来源不会被自动投递。
- AC-AUTO-04：服务重启后，已排队任务可由 Worker 继续执行。
- AC-AUTO-05：手动同步与自动同步并发触发时仍保持单任务幂等。
- AC-AUTO-06：同步成功后正确计算下一次时间；失败后按策略退避且不形成忙循环。

# 6. 能力二：最近使用排序

## 6.1 业务定义

最近使用不是最近同步。来源在用户通过知识库进入该来源内容时，应原子更新：

```text
last_opened_at
last_opened_by（项目存在可靠用户身份时才写）
```

禁止仅因为后台同步、统计查询或列表刷新而更新最近使用时间。

## 6.2 API 与排序

增加明确的打开/访问记录入口，或复用现有真实文档访问链路，但必须保证行为可测试。例如：

```text
POST /api/v1/knowledge-sources/{id}/opened
```

响应可使用 `204 No Content`。如果项目已有统一访问事件接口，优先复用。

扩展排序枚举：

```text
sort_by=last_opened
sort_order=desc
```

排序要求：

1. 置顶优先规则与当前产品契约保持一致；
2. 非空 `last_opened_at` 按时间排序；
3. 从未打开的来源排在已打开来源之后；
4. 最后使用稳定 ID 作为确定性 tie-breaker；
5. 分页前在数据库完成排序。

## 6.3 验收标准

- AC-RECENT-01：记录打开后，来源的 `last_opened_at` 实际持久化。
- AC-RECENT-02：列表刷新、统计请求和同步不会错误更新时间。
- AC-RECENT-03：最近使用排序在分页前执行且结果稳定。
- AC-RECENT-04：从未使用来源稳定排在最后。
- AC-RECENT-05：不存在认证身份时不得伪造用户 ID。

# 7. 能力三：关联研究项目搜索与筛选

## 7.1 先复用真实领域模型

先审计 `research_context`、研究项目或工作区模型。禁止新建与现有研究项目重复的表。

如果现有领域对象是 ResearchContext，则新增显式多对多关联表，例如：

```text
knowledge_source_research_contexts
- knowledge_source_id
- research_context_id
- created_at
- created_by（仅在身份可靠时）
```

联合主键或唯一约束必须阻止重复关联。删除关联不应删除来源、研究项目或磁盘文件。

## 7.2 API

提供最小必要能力：

```text
GET    /api/v1/knowledge-sources/{id}/research-contexts
PUT    /api/v1/knowledge-sources/{id}/research-contexts/{context_id}
DELETE /api/v1/knowledge-sources/{id}/research-contexts/{context_id}
```

扩展分页查询：

```text
research_context_id=<id>
q=<名称、路径或关联研究项目名称>
```

明确搜索语义：普通文本 `q` 同时覆盖来源名称、来源路径、关联研究项目名称；精确研究项目筛选使用 `research_context_id`。

查询必须：

- 使用参数化 SQL；
- 避免多对多 JOIN 导致来源重复；
- `total` 统计去重来源；
- 搜索、筛选、排序全部在分页前执行；
- 避免逐条 N+1 查询。

## 7.3 响应契约

来源列表可以返回精简关联信息，但不得把完整研究项目对象塞入每一项。推荐：

```json
{
  "research_contexts": [
    {"id": 12, "name": "ILD Biomarker Study"}
  ],
  "research_context_count": 1
}
```

## 7.4 验收标准

- AC-RESEARCH-01：可以建立和解除关联，重复关联返回幂等成功或明确冲突。
- AC-RESEARCH-02：按研究项目 ID 筛选在分页前执行，`total` 正确。
- AC-RESEARCH-03：文本搜索可以命中关联项目名称且不产生重复来源。
- AC-RESEARCH-04：来源或研究项目不存在时返回明确 404。
- AC-RESEARCH-05：解除关联不删除任何业务实体或源文件。

# 8. 能力四：安全打开已有来源目录

## 8.1 强制安全模型

该能力只能用于运行在用户本机桌面环境的受信部署。服务器部署、容器部署、远程多用户部署默认必须禁用。

禁止接受客户端提交的任意路径：

```json
{"path": "C:\\..."}
```

客户端只能提交稳定的 `source_id`。服务端从数据库读取路径并重新执行路径授权与可用性检查。

## 8.2 API

推荐：

```text
POST /api/v1/knowledge-sources/{id}/open-directory
```

成功返回 `204` 或类型化响应。必须通过应用配置开关控制，例如：

```text
ENABLE_LOCAL_DIRECTORY_OPEN=false
```

这只是项目应用配置，不得自动修改系统环境变量或系统设置。

## 8.3 操作系统适配

将操作系统调用封装在独立 Adapter 中：

- Windows：使用安全参数传递调用 Explorer，不拼接 shell 命令；
- macOS/Linux：只有项目明确支持时才提供适配；
- 不使用 `shell=True`；
- 不把用户路径拼入命令字符串；
- 不允许 URL、UNC/网络路径或符号链接逃逸，除非产品明确授权并有专项安全测试；
- 不返回完整绝对路径给无权限调用方；
- 记录来源 ID、结果和错误类别，不记录敏感路径正文。

API 进程运行在远程服务器时，“打开目录”只会打开服务器目录，因此必须返回明确的 `FEATURE_UNAVAILABLE`，不能假装成功。

## 8.4 验收标准

- AC-OPEN-01：客户端不能提交任意路径，只能使用已有来源 ID。
- AC-OPEN-02：功能关闭或非本机模式时返回明确 4xx，不执行系统调用。
- AC-OPEN-03：来源不存在、已暂停、路径缺失、不可访问分别返回稳定错误。
- AC-OPEN-04：操作系统 Adapter 使用参数数组且不启用 shell。
- AC-OPEN-05：恶意路径、符号链接逃逸和未授权网络路径被拒绝。
- AC-OPEN-06：测试使用 mock Adapter，不在自动测试中真的打开资源管理器。

# 9. 能力五：精确同步进度百分比

## 9.1 原则

禁止随机进度、基于时间猜测进度或固定显示 65%。进度必须来源于本次同步任务实际工作量。

同步进度属于任务实例，不应只存放在知识来源记录上。一个来源的历史任务必须能区分。

## 9.2 进度模型

为任务详情或专用进度表保存：

```text
phase: queued | scanning | hashing | persisting | parsing | indexing | finalizing
completed_units: int
total_units: int | null
progress_percent: int
current_item: string | null（必须脱敏或只返回文件名）
updated_at: datetime
```

推荐进度规则：

- 在目录扫描完成前，`total_units` 可能未知；API 返回 `progress_percent=null` 或明确的 indeterminate 状态；
- 获取真实文件总量后，根据已完成工作单元计算；
- 百分比单调不下降；
- 运行中最大 99，只有事务提交且任务成功后才为 100；
- 失败和取消保留最后真实进度，不伪造 100；
- 重试任务应有新的 attempt 或清晰重置策略，不能混淆两次执行。

如果解析、索引工作量差异显著，可以使用经文档化的阶段权重，但权重必须由常量定义且测试单调性。优先使用真实 `completed_units / total_units`。

## 9.3 API

复用现有任务查询响应，增加类型化字段，避免另建重复状态源：

```json
{
  "status": "running",
  "phase": "parsing",
  "completed_units": 35,
  "total_units": 50,
  "progress_percent": 70,
  "updated_at": "..."
}
```

进度更新应节流，避免每处理一个小片段都提交数据库。节流策略不能导致任务结束时遗漏最终状态。

## 9.4 验收标准

- AC-PROGRESS-01：扫描前返回不确定进度，不伪造百分比。
- AC-PROGRESS-02：确定总量后，百分比来自真实完成单位并单调递增。
- AC-PROGRESS-03：成功提交后才为 100；失败任务绝不为 100。
- AC-PROGRESS-04：Worker 重启后可以读取最后持久化进度。
- AC-PROGRESS-05：并发读取进度不会影响同步事务。
- AC-PROGRESS-06：大量文件下进度写入经过节流，不形成明显写放大。

# 10. 能力六：完整 Obsidian 知识关系能力

## 10.1 本阶段支持范围

必须明确“完整”的边界。本次至少支持：

- Markdown 笔记；
- YAML Frontmatter；
- `[[Wiki Link]]`；
- `[[Target|Alias]]`；
- `![[Embedded Note]]`；
- Markdown 相对链接；
- 标题锚点和块引用标识（若无法解析为具体块，至少保留原始 locator）；
- `#tag` 与 Frontmatter tags；
- Backlink 查询；
- 未解析链接（dangling link）；
- 文件重命名、移动、删除后的关系更新；
- 增量同步和幂等重建。

默认不解析第三方插件私有语法、Canvas、Dataview 查询执行结果或远程资源。若项目决定支持，必须作为独立后续能力，不得在本次静默扩大范围。

## 10.2 数据模型

不要把关系存成一个不可查询的大 JSON。根据现有 Document 模型设计规范化表，建议：

```text
knowledge_nodes
- id
- knowledge_source_id
- document_id
- canonical_key
- title
- relative_path
- content_hash
- created_at
- updated_at

knowledge_edges
- id
- knowledge_source_id
- source_node_id
- target_node_id nullable
- raw_target
- normalized_target
- relation_type
- locator nullable
- is_resolved
- created_at

knowledge_tags
- id
- normalized_name unique
- display_name

knowledge_node_tags
- node_id
- tag_id
```

约束和索引至少覆盖：

- 来源内 canonical key 唯一；
- 边的幂等唯一键；
- source/target node 查询；
- 未解析链接查询；
- tag 反查；
- 删除来源时数据库关系级联删除，但永远不删除 Vault 原始文件。

## 10.3 解析与解析消歧

解析器必须是无数据库依赖的纯函数，输出类型化中间结果。关系解析 Service 再负责数据库匹配。

链接解析需要定义：

1. 路径规范化和大小写策略；
2. 同名笔记的消歧规则；
3. Alias 不改变目标 canonical key；
4. 标题锚点和块 ID 的保存方式；
5. 无目标时保留 dangling edge；
6. 目标后续出现时可重新解析；
7. 文件移动或删除时旧边不会残留为错误已解析状态。

不得访问 Vault 目录之外的文件。对 Markdown 链接进行路径解析时必须防止 `..`、绝对路径和符号链接逃逸。

## 10.4 API

新增独立关系模块，避免把图谱查询塞进知识来源 Router。推荐最小接口：

```text
GET /api/v1/knowledge-sources/{source_id}/relations/summary
GET /api/v1/knowledge-sources/{source_id}/nodes
GET /api/v1/knowledge-sources/{source_id}/nodes/{node_id}
GET /api/v1/knowledge-sources/{source_id}/nodes/{node_id}/backlinks
GET /api/v1/knowledge-sources/{source_id}/relations/unresolved
GET /api/v1/knowledge-sources/{source_id}/tags
```

所有列表必须分页。关系摘要可以返回：

```text
node_count
edge_count
resolved_edge_count
unresolved_edge_count
tag_count
last_built_at
```

禁止直接返回整个 Vault 的全部节点和边。

## 10.5 与同步流水线集成

Obsidian 关系构建必须接入已有持久化同步任务：

```text
扫描/解析文档
→ 为发生变化的 Obsidian 笔记更新节点
→ 重建受影响的出边
→ 尝试解析新出现目标对应的 dangling edges
→ 清理被删除节点的解析状态
→ 原子提交本批结果
```

普通本地文件夹不得被错误当成 Obsidian Vault 构建 WikiLink 关系，除非产品以后明确支持。

## 10.6 验收标准

- AC-OBS-01：WikiLink、Alias、Embed、Markdown 相对链接和 Tag 被正确解析。
- AC-OBS-02：Backlink 查询返回真实反向关系。
- AC-OBS-03：不存在目标产生可查询的 dangling edge；目标出现后可解析。
- AC-OBS-04：同一 Vault 重复同步不会产生重复节点、边或标签。
- AC-OBS-05：文件修改、移动、重命名和删除后关系保持一致。
- AC-OBS-06：恶意相对路径和符号链接不能逃逸 Vault。
- AC-OBS-07：大 Vault 查询使用分页和索引，禁止一次加载完整图谱。
- AC-OBS-08：删除知识来源只删除数据库派生关系，不删除用户 Vault 文件。

# 11. 迁移要求

1. 新建 Alembic revision，不修改已经存在的历史迁移。
2. 升级迁移必须为现有数据提供安全默认值或可空过渡。
3. 创建索引、唯一约束和外键时考虑 SQLite 与生产数据库兼容性。
4. Downgrade 不得删除知识来源、文档或研究项目主数据；仅移除本次新增表和字段。
5. 运行并记录：

```text
alembic heads
alembic upgrade head
alembic check
alembic downgrade <previous_revision>
alembic upgrade head
```

只能在测试数据库执行 downgrade 验证，禁止对用户真实数据库执行破坏性回退。

# 13. 测试策略与强制门禁

每条验收标准必须至少对应一个行为测试，并建立追踪表：

|---|---|---|---|---|
| AC-AUTO-01 | 集成 | 待填写 | 待验证 | 待验证 |

实施顺序必须是：

```text

```

至少覆盖：

- 单元测试：时间计算、进度计算、Obsidian 解析、路径验证；

- Worker 测试：幂等、租约、心跳、重启恢复、失败退避；
- 安全测试：任意路径、命令注入、路径穿越、符号链接逃逸；
- 性能边界测试：大量来源、大量笔记、关系分页、进度写放大。
